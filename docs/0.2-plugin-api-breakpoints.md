## 六处断点

### 1. `engines.dsh`

从 0.2.1-alpha.3 的下一版起（rc.3 已包含），安装和 profile 启动只读包自己的 `engines.dsh`。写了它，`@deepseek-ai/dsh*` 的 peer 就不再放宽或收窄结果。没写它，才退回检查这些 peer。两者都没有，则不设版本约束，直接允许装入。`engines` 不是对象，或 `engines.dsh` 不是字符串，清单视为损坏并拒绝。`workspace:` 写进 `engines.dsh` 也算无效。

0.1.5-rc.2 的 boot/CLI 源码里没有 `engines.dsh` 这个词，不读该字段。所以给 desk-panel 加上只覆盖 0.2 的范围，不会挡住仍停在 0.1.5 的 WSL 重装。

预发布参与范围比较。`>=0.2.1-rc.3 <0.3.0` 盖住 rc.3，盖不住 rc.2，也盖不住 0.1.5。

不兼容的 bundle 不会被 import：启动时跳过，记在 `skippedBundles`。没有 `engines.dsh`、也没有 DSH peer 的包不在此列。

### 2. 子路径导出

0.2.0-rc.2 的下一版起，子路径插件不再读 `<子路径>/package.json`。标题和描述只来自导出的 `<子路径>/locale/*.json`（`meta.title` / `meta.description`），图标来自导出的 `<子路径>/icon`。包根插件仍用 `package.json` 的文案；省略 `icon` 时，导出的 `./icon` 提供图片。

同一窗口里，运行时不变式被删除：不再发布 `@deepseek-ai/dsh-invariants`，也不再发布任何官方包的 `./invariant` 子路径。插件自己如果还导出 `./invariant` 并 `inject: ['invariants']`，加载时会找不到服务。

| `settings.models.footer` | list | 仍是 list |
| `settings.general.item` | list | 仍是 list |
| `settings.plugins.tab` | 插件页里的标签 | 仍在；插件页改由它承接 |
| `settings.plugin.item` | keyed（必须带 `key`） | 已删除。models 的注释还提这个名字，源码里没有声明 |
| `sidebar.footer.action` | list | 仍是 list；owner 为 `{ wide }` |
| `sidebar.right.pane.tab` | 有 | 仍有 |
| `conversation.session.header.utilities` | list | 仍是 list |

| `conversation.composer.dock` | list，官方只注册一行 | 仍是 list，官方改注册两行（见下） |

`window.__ModuleLoader__.load({ id, factory })` 还在。平台种子仍包含 `react` 和 `@deepseek-ai/dsh-client-ui-slots`。`dsh.client.inject` 仍是包名依赖，不是 Cordis 服务注入；多出来的非种子模块请求走 `dsh.client.external`。

### 4. stats → activity / usage

0.1.5 的 `ui-chat` 往 `conversation.composer.dock` 注册一行：`id: 'stats'`。

0.2.1-rc.3 拆成两行，都在同一槽上：

- `id: 'activity'`，order 0：轮次、步骤、输出速度
- `id: 'usage'`，order 1：token 与缓存命中

要换掉官方统计条，必须用相同 id 和相同 order 各注册一次。只覆盖旧的 `stats` 不会命中任何一行，统计条保持官方的两枚。新 id 是加一枚控件，不是替换。控件带 `data-composer-stat`。

这和门户账本的「工作台用量」不是同一个入口。

### 5. profile bundles

机制没换：包声明 `dsh.bundle.patch`（一个文件或有序文件列表），`dsh plugin --profile <name> add` 把包名追加进 `dsh.profile.bundles`。层序仍是 base，然后按安装顺序的 bundle，然后 profile 自己的 `cordis.patch.yml`，然后 `$DSH_HOME/cordis.patch.yml`。覆盖一行是整份 `config` 替换，不是深合并。

`file:` 装进去的是副本。清单或 `client.js` 改了，已有 profile 不会自己更新。HMR 开着的 profile（官方 web 模板开着）对已安装的 spec 再 `add` 会得到 `already-installed`，不跑 pnpm。要换版本或换路径，先 `remove` 再 `add`。

### 6. plugin CLI

0.2.1-alpha.1 起，`dsh plugin` 只在转发给 pnpm 的参数之前认识 `--profile`。`dsh plugin add <pkg> --profile web` 会因缺少 `--profile` 失败。正确写法是 `dsh plugin --profile web add <pkg>`。`--help` 也不再无条件转发给 pnpm。

另外：`dsh --profile web --dump-config-schema` 可以在不挂载的情况下看补丁行的 schema。这次没有拿它做 CI。

## 插件对照

根插件，不是子路径插件。已导出 `.`、`./client`、`./cordis.patch.yml`、`./package.json`。展示文案继续走 `package.json`。

### `plugin/dsh-agents-md`（已改结算，`file:` 0.4.0）

根插件，无 `dsh.client`，无 `@deepseek-ai/dsh*` peer。`engines.dsh` 为 `>=0.2.1-rc.3 <0.3.0`。

0.3.0 在 rc.3 上会坏，不要用 `link:` 装回去：

- 它从 `packages/subagent/subagent/lib/index.js` 要 `settleRun`。rc.3 的公开导出是 `settleRunResult`（`export * from './out-of-process.ts'`），没有 `settleRun`。`settleRunResult` 只结算进程外 attempt，不能拿来结算一次委派。
- 0.2.1-alpha.1 起，委派改成受管理的 activation：`start()` / 前台 `settleRun` / `{ kind: 'background', jobId }` 被 `startActivation()` 和完成通知替换。`backgroundMode`、`run_in_background`、`job_output` / `job_kill` 收结果的路径不再成立。
- `defineTool` 仍从 `@deepseek-ai/dsh-tools` 导出。`ctx.systemPrompt.section` 也还在。这两处不是断点。

0.4.0 的委派调用 `ctx.subagents.startActivation({ provider, label, request, signal, delivery: 'parent' })`，立刻返回 `{ kind: 'activation', subagentId }`。完成通知由运行时投递给父会话；插件自己的 `subagent/end` 钩子仍按 `childId` 转发通知桥。rc.3 的请求没有 `persona` / `toolFilter`（这两项属于 agent preset）。定义正文和工具名单写进 `request.prompt`。

bootstrap 与 member-provision 钉 `file:plugin/dsh-agents-md`。`DEFERRED_PLUGINS` 不再包含 `dsh-agents-md`。已是 0.4.0 且副本与仓库一致则留下；其它安装先卸再装。

## 本地冒烟（http://127.0.0.1:18080）

用空卷。不要挂东京的数据卷，也不要把容器里的引擎指到 WSL 的 `~/deepseek-harness`。

```bash
cp .env.example .env
# 至少写上：
#   ANYWORK_HOST=127.0.0.1:18080
#   ANYWORK_PORT=18080
#   ANYWORK_BIND=127.0.0.1
#   DEEPSEEK_API_KEY=<真 key>
docker compose up -d --build
curl -fsS http://127.0.0.1:18080/healthz
```

然后：

1. 浏览器打开 `http://127.0.0.1:18080/`，用管理员账号登录。`ANYWORK_HOST` 必须和地址栏一致，含端口。
2. 进入该成员的工作台。设置里应有「工作台用量」。直连实例端口看不到账本，这是预期。
3. 侧栏底部应有 desk-panel 的入口（公告、助理等）。右侧 better-sidebar 来自启动脚本钉的 `dsh-better-sidebar@0.28.0`。玻璃主题开关来自启动脚本钉的仓内 `dsh-client-ui-aqua@1.4.2`（`settings.general.item`）。玻璃已经开着时，通用设置里仍应有「玻璃主题」总开关和旋钮。
4. 容器日志里不应再有对 `dsh-better-sidebar@0.19.1`、aqua git、npm `dsh-client-ui-aqua@1.3.1`、`dsh-chat-import@0.19.3` 的安装记录，也不应再 `link:` 安装旧的 `dsh-agents-md`。应安装 `dsh-better-sidebar@0.28.0`、`file:plugin/dsh-client-ui-aqua`、`file:plugin/dsh-agents-md` 与 `dsh-chat-import@0.26.2`（已是对应版本则跳过）。从 0.1.5 卷升上来时，agents-md 若不是 0.4.0 副本、better-sidebar 若不是 0.28.0、aqua 若不是 1.4.2、chat-import 若不是 0.26.2，启动脚本卸下后按该钉重装。
5. 改一次语言或外观后刷新，设置应还在（门户注入了 `__DSH_HOST_PERSISTENCE__`，general 的 document store 已放行）。

首次构建要编译 dsh，时间很长。构建失败时先看 branding / settings 补丁有没有在 `ui-settings-general` 上报错退出。
